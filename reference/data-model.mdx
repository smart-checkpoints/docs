title: "Data model"
description: "The SQLite tables behind the graph."
---

The server stores everything in one SQLite file, `database.db`, created next to
`server.js` on first run. It runs in WAL mode. The schema is created and
migrated at startup, and a failed migration stops the server rather than letting
it serve wrong positions.

## Migrations

The schema is brought up to date at startup, and any failure stops the server.

- `nodes.x_coord` / `nodes.y_coord` are renamed to `longitude` / `latitude`
  (the old mapping was x = longitude, y = latitude, so no values move).
- `connections` gains `distance_status` and `distance_updated_at`. Existing rows
  with a distance above zero become `ok`; every other row becomes `unknown` with
  the distance nulled, to be recalculated when a driver next connects.
- `connections` gains `path`, `path_format`, `endpoint_offsets`, and
  `endpoints_hash`. No backfill: a pre-existing edge has no geometry and a NULL
  hash, which reads as "moved", so it is recalculated once.
- `projects` gains the four `map_driver` columns, defaulting to status `none`.

## Retention

`traversals` is the only table the server prunes, and only to the last five
minutes. `violations` grows without bound, and `car_data` holds one row per
plate that has ever been seen by the project.

<Note>
  A violation records the plate, the average speed, and the time. It does not
  record which edge it happened on. If you need that, read it from the
  `traversals` row with the matching timestamp.
</Note>

<Warning>
  Every timestamp in a TEXT column is ISO 8601 in UTC, which is also what the
  REST API accepts and what the realtime events carry. Databases created before
  this hold `violations.timestamp` as stringified epoch milliseconds, such as
  `"1787905380236.0"`, which no client can parse back into a time. Rows written
  from now on are ISO; old rows are left as they are, and the console reads
  both.
</Warning>
