The server serves an operator console at its own root. It is the same interface
the REST API and the [realtime channel](/reference/realtime) expose, drawn for a
person: a list of the projects on the server, a live view of one project's
checkpoint graph with its diagnostics and its camera keys, and a table of every
project for whoever holds the admin password.

The console is a static site. It is built from the `console/` directory in the
server repository, and the same Express process that answers the API serves the
build where it lands, so there is no second server, no second port, and no cross
origin anywhere.

<Info>
  The console runs the same stack and the same design system as
  [smartcheckpoints.xyz](https://smartcheckpoints.xyz): Next.js, TypeScript,
  Tailwind and one set of tokens. A colour, a type step or a button that changes
  on the website changes here too.
</Info>

## Building it

The build is generated and is not in version control. After cloning the server,
or after any change under `console/`:

```bash
npm install
npm run build   # builds the console into console/out
npm start
```

A server whose console has not been built still answers the REST API and both
realtime channels normally. Only the pages are missing, and the pages say so.

## Projects

`GET /` lists every project on the server, each with the shape of its graph, its
name, and how many checkpoints and edges it holds. The list is unauthenticated,
because [`GET /list-projects`](/reference/rest-api) is.

The shapes are not. Thumbnail geometry comes from
`GET /project/{id}/thumbnail-data`, which projects the nodes onto the local
tangent plane and normalises them into the unit square before sending them, so a
thumbnail carries the shape of a deployment and never a camera's position.

Opening a project needs its API key. There is no URL that opens a project on its
own.

## The graph

`GET /project` is the live view of one project. It has two views of the same
geometry, toggled in the corner:

- The **graph view** draws straight lines on a blank background. It is always
  available, needs no driver, and is the only view that edits.
- The **map view** embeds a [map driver's](/reference/map-bridge) page, drawing
  the real road shapes a distance driver measured on a basemap. It exists only
  while a map driver is connected and its address is approved, and the console
  falls back to the graph view whenever it is not there.

These gestures are the graph view's:

| Gesture | What it does |
| --- | --- |
| Drag the background | Pans |
| Wheel | Zooms about the pointer |
| Drag from one checkpoint to another | Drafts an edge between them |
| Shift-drag a checkpoint | Proposes a move to that position |
| Click an edge | Opens it for editing |
| <kbd>F</kbd> | Frames the whole graph |
| <kbd>+</kbd> / <kbd>-</kbd> | Zooms |
| <kbd>Esc</kbd> | Closes whatever is open |

Checkpoints are drawn at a constant size on screen, whatever the zoom, so a
graph that spans a city stays as clickable as one that spans a junction. The
grid and the scale bar are in metres: this system enforces speed over real
driving distance, and the view says how far a screen length actually is.

### What the colours mean

Colour follows the same rule as everywhere else in the system. The accent draws
structure. The status colours mean something is measured, or something is wrong.

| Colour | Meaning |
| --- | --- |
| Cyan | A checkpoint, and an edge that is enforcing: `distance_status` of `ok` |
| Dashed | An edge with `distance_status` of `unknown`. Nobody has resolved its distance; it cannot enforce anything |
| Dotted | An edge with `distance_status` of `no-route`. A driver said there is no road here |
| Green to red | Live congestion, from free flowing to twice the expected travel time |
| Red pulse on a checkpoint | A sighting just arrived at it |

Everything on this page is live over the realtime channel. Checkpoints and edges
created by cameras or by another operator appear as they are created, checkpoints
that are moved jump to their new position, violations arrive as they are
recorded, and both the distance driver's status and the map driver's status
change with them.

### Editing an edge

An edge carries two numbers, and enforcement is arithmetic on them: distance in
metres, and the speed limit in km/h enforced as an average across it.

<Note>
  While a [distance driver](/concepts/distance-drivers) is attached, the console
  keeps the distance field read-only and lets you edit only the speed limit. The
  driver owns the distance, and mixing a hand-typed number with routed ones
  makes it unclear which is which. Editing only the limit leaves the stored
  distance and its status untouched.
</Note>

### Adding a checkpoint

Cameras normally create their own checkpoints over
[`POST /create-node`](/reference/rest-api) as they come online. The console can
also place one from a WGS84 coordinate pair, for laying a graph out ahead of the
hardware. It validates the pair with the same rules the server applies on the
way in.

### Moving a checkpoint

Shift-drag a checkpoint to propose a new position. The graph is geometrically
faithful, so the drop point is a real coordinate. Nothing is sent until a dialog
confirms it: it shows how far the camera would move in metres and how many
connections stop enforcing as a result, because every distance measured to that
checkpoint is discarded on a move. See [Correcting a checkpoint's
position](/concepts/data-quality#correcting-a-checkpoint-s-position).

## Data quality

A panel on the project view shows what
[`GET /project/{id}/diagnostics`](/reference/rest-api#data-quality) returns:
checkpoints that look mispositioned and edges whose road distance does not match
the straight line. It is recomputed when the panel is opened and when you ask.
Every flag is shown with the numbers behind it and the thresholds it was judged
against. See [Data quality](/concepts/data-quality).

## Reporter keys

A panel on the project view issues, lists, and revokes the per-camera
[reporter keys](/reference/rest-api#reporter-keys). A new key is shown in full
exactly once, when it is issued; after that the list shows only a six-character
prefix, enough to tell one camera's key from another's. Issuing them needs the
project's operator key, which is the one the console holds.

## The map view

The map view is served by a separate **map driver** process and embedded in an
`<iframe>`. Before the console will embed it, an operator approves the address
the driver announced, under **Project**. Approving, rejecting, and revoking that
address all happen here. If a driver's socket is up but its page will not load,
the console says so over the frame and names the address. See [The map
bridge](/reference/map-bridge).

## Administration

`GET /admin` lists every project on the server together with its API key, behind
the `ADMIN_PASSWORD` set in the server's environment.

The password is held in the page for as long as it is open and is never stored,
so a reload asks for it again. Keys are masked until you ask for one.

<Warning>
  A server with no `ADMIN_PASSWORD` set has administration switched off, and this
  page will say so rather than let anyone in.
</Warning>

## How credentials are held

The console holds a project's **operator key**: full read and write on the
project, and the key a distance driver and an administrator also use. Cameras in
the field hold narrower [reporter keys](/reference/rest-api#reporter-keys),
issued from the console. The console treats the operator key accordingly.

- It is held in `sessionStorage`, scoped to one tab and gone when that tab
  closes.
- It travels in the `x-api-key` header, never in a URL. A key in a query string
  ends up in browser history, in the `Referer` of anything the page loads, and
  in every proxy log along the way.
- It is masked wherever it is displayed, and revealing it is a deliberate act.

A project's key is shown in full exactly once, when the project is created.
Nothing on the server will show it again to someone who does not already hold
it.
